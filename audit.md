# Аудит безопасности (http-conf)

Дата: 2026-02-24  
Область: FastCGI HTTP listener/connection, маршрутизация сообщений, auth/JWT, обработка входных данных.

## Критичные и высокие риски

### 1) Обход авторизации при маршрутизации `/api/message/send` (Critical)
- Файл: `src/actors/CONNECTION/common/route_send.cpp:28`
- Проблема: вызывается `domain->auth(...)`, но результат не проверяется, и не проверяется роль пользователя перед форвардом.
- Файл: `src/actors/CONNECTION/common/route_send.cpp:43-45`
- Дополнительно: клиент сам задает `ws` и `route` (после schema validation), что позволяет неаутентифицированному клиенту пробовать вызывать внутренние маршруты воркспейсов.
- Риск: несанкционированный доступ к внутренним действиям/данным, горизонтальное перемещение по внутренней шине сообщений.
- Рекомендации:
1. Явно проверять результат `auth` и роль (`ROLES::SESSION::USER`/выше) до `tegia::message::send(...)`.
2. Ввести allowlist для `ws` и `route`, разрешать только безопасный набор публичных маршрутов.
3. На уровне схемы и бизнес-логики разделить публичные и внутренние маршруты.

### 2) Небезопасная логика `auth()` (High)
- Файл: `src/common/domain.cpp:23-91`
- Проблема:
1. При отсутствии токена (`case 0`) функция возвращает `true`.
2. При одновременном наличии Bearer и cookie (`case 11`) выставляется `is_auth = false` (нестандартное поведение, возможен DoS/ложные отказы).
3. Результат `jwt->status()` не влияет на возвращаемое значение `is_auth`.
- Риск: вызывающий код может считать запрос аутентифицированным при невалидной/пустой авторизации.
- Рекомендации:
1. Возвращать `false`, если токен отсутствует.
2. Возвращать `false`, если `jwt->status()` неуспешен.
3. Определить приоритет источника токена (например, `Authorization` > cookie) и убрать ветку `WTF???`.

### 3) Утечка чувствительных данных в логи (High)
- Файл: `src/common/connection.cpp:173-194, 236-240, 269-273, 430-431`
- Проблема: в debug-лог пишутся все env-параметры, cookie, тело POST, что может включать `Authorization`, JWT, персональные данные, секреты.
- Риск: компрометация токенов и пользовательских данных через журналы.
- Рекомендации:
1. Немедленно редактировать/маскировать `Authorization`, `Cookie`, чувствительные поля JSON.
2. Отключить `_LOG_DEBUG_` для production-сборок.
3. Добавить политику хранения/ротации/доступа к логам.

### 4) DoS по памяти/размеру тела запроса (High)
- Файл: `src/common/connection.cpp:256-267, 284-328`
- Проблема: `CONTENT_LENGTH` без лимитов читается полностью в память (`new char[content_length+1]`, затем `std::string`). Для multipart также сначала загружается целиком в память.
- Риск: исчерпание памяти и падение процесса при больших запросах.
- Рекомендации:
1. Ввести server-side лимит (например, `max_request_body_bytes`) и возвращать `413` до чтения тела.
2. Перейти на потоковое чтение и потоковую запись multipart-файлов.
3. Дублировать ограничения в nginx (`client_max_body_size`, таймауты).

## Средние риски

### 5) Потенциальное падение на malformed cookie (Medium)
- Файл: `src/common/connection.cpp:243-247`
- Проблема: код предполагает, что после split по `=` всегда есть `tmp[1]`; при некорректном cookie возможен выход за границы.
- Риск: аварийное завершение процесса от специально сформированного заголовка.
- Рекомендации:
1. Проверять `tmp.size() >= 2`.
2. Корректно обрабатывать `=` внутри значения cookie.

### 6) SQL-инъекция в запросе workspace (Medium)
- Файл: `src/common/ws.h:47`
- Проблема: SQL строится конкатенацией `wsid`.
- Риск: при достижимости этого кода из внешнего ввода возможно чтение/модификация БД.
- Рекомендации:
1. Использовать параметризованные запросы/prepared statements.
2. Валидировать формат `wsid` (например, UUID regex) до запроса.

### 7) Возможность остановки процесса через `exit(0)` (Medium)
- Файл: `src/actors/CONNECTION/actions/response.cpp:272-277`
- Проблема: для неожидаемого сочетания `status/type` вызывается `exit(0)`.
- Риск: отказ в обслуживании при некорректном внутреннем сообщении.
- Рекомендации:
1. Заменить на безопасный fallback (`500 Internal Server Error`) без завершения процесса.
2. Логировать ошибку и продолжать обработку следующих запросов.

### 8) Публичные тестовые действия в прод-коде (Medium)
- Файл: `src/actors/CONNECTION/CONNECTION.cpp:18-19`, `src/actors/CONNECTION/actions/test.cpp:24-44`
- Проблема: `/test/01` и `/test/02` доступны PUBLIC и выполняют `sleep_for(2s)`.
- Риск: упрощенный DoS (занятие воркеров/потоков).
- Рекомендации:
1. Удалить тестовые эндпоинты из production.
2. Либо ограничить ролью SYSTEM и сборочным флагом debug-only.

## Низкие риски и hardening

### 9) Недостаток защитных HTTP-заголовков (Low)
- Файл: `src/actors/CONNECTION/actions/response.cpp`
- Проблема: отсутствуют базовые security headers (`X-Content-Type-Options`, `Referrer-Policy`, при HTTPS также HSTS).
- Рекомендации:
1. Добавить стандартный набор заголовков для API-ответов.
2. Зафиксировать политику CORS на allowlist origins (если CORS включается).

### 10) Временные upload-файлы без жизненного цикла (Low/Medium)
- Файл: `src/common/connection.cpp:126-153, 353-366`
- Проблема: файлы сохраняются в `/tmp`, но в этом компоненте не видно удаления/TTL-контроля.
- Риск: заполнение диска, накопление чувствительных данных во временной директории.
- Рекомендации:
1. Ввести cleanup-политику (удаление после обработки, фоновой GC, TTL).
2. Ограничить права/доступ к директории временных файлов.
