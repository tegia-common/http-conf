# Загрузка больших файлов (до 100 МБ)

Ниже перечислены доработки, которые нужны в этом репозитории и в обвязке (nginx), чтобы безопасно принимать большие запросы.

## 1) Ограничение на стороне nginx

В `server`/`location`, который проксирует в FastCGI, нужно явно поднять лимит тела запроса:

```nginx
client_max_body_size 100m;
```

Дополнительно рекомендуется настроить таймауты для медленной загрузки:

```nginx
client_body_timeout 120s;
fastcgi_read_timeout 120s;
```

## 2) Конфигурируемый лимит в приложении

Сейчас размер тела не валидируется конфигом и безусловно читается в память.

Что стоит сделать в коде:

- добавить параметр вроде `max_request_body_bytes` в схему `/init`;
- пробросить его в обработку `connection_t::init()`;
- если `CONTENT_LENGTH` больше лимита — возвращать `413 Payload Too Large` и не читать тело.

Для цели 100 МБ разумное значение по умолчанию:

```text
104857600
```

## 3) Отказ от чтения всего тела в память одним буфером

Сейчас тело читается через `new char[content_length+1]` и затем целиком превращается в `std::string`.
Для больших файлов это даёт высокий расход памяти на процесс.

Рекомендуется:

- читать входной поток чанками (например, по 64 КБ);
- для `multipart/form-data` сохранять файл во временный файл/хранилище, а не в JSON-поле;
- вводить отдельный путь обработки upload-запросов вместо универсального JSON-парсинга.

## 4) Наблюдаемость и защита

- логировать `CONTENT_LENGTH`, время чтения тела и итоговый статус;
- ввести rate-limit/ограничение параллельных upload-запросов на уровне nginx;
- добавить тест-кейс на загрузку файла 100 МБ и на ожидаемый `413` при превышении лимита.

## Минимальный рабочий план

1. В nginx: `client_max_body_size 100m`.
2. В приложении: проверка `CONTENT_LENGTH <= 104857600` до чтения тела.
3. Для `multipart/form-data`: потоковая запись во временный файл.
4. Нагрузочный тест с файлом 100 МБ.
