# Архитектурный принцип: границы репозиториев и ответственности

## 1. Контекст

`configurations/http-conf` не является полным хост-приложением.  
Этот репозиторий содержит подключаемые библиотеки/модули и конфигурационные компоненты, которые используются внешним приложением.

Хост-приложение находится в отдельном репозитории.  
`tegia-sdk` в этом репозитории предоставляет SDK-контракт, доступный библиотечному коду.

## 2. Принцип разделения ответственности

1. Логика библиотек реализуется и тестируется в текущем репозитории.
2. Логика интеграции в runtime-приложения реализуется и тестируется в репозитории приложения.
3. Кросс-репозиторные задачи фиксируются явно в каждой task-документации с разбивкой:
   - что делается здесь (library scope),
   - что делается в приложении (application scope).

## 3. Что относится к library scope (этот репозиторий)

1. Алгоритмы и helper-функции, поставляемые библиотекой.
2. Безопасность и корректность API/заголовков на уровне библиотечного кода.
3. Unit- и component-тесты библиотечных функций.
4. Документирование библиотечных контрактов и ограничений.

## 4. Что относится к application scope (отдельный репозиторий)

1. Runtime-интеграция библиотек в конкретные сервисы/маршруты.
2. E2E/интеграционные проверки в полном окружении приложения.
3. Конфигурация веб-сервера/прокси и отсутствие конфликтующих переопределений.
4. Бизнес-правила оркестрации, которые выходят за пределы библиотечного контракта.

## 5. Обязательное правило для task-документов

Для задач, затрагивающих оба контура, task-документ должен содержать отдельный раздел:

1. `Этот репозиторий` (конкретные изменения в коде и тестах библиотеки).
2. `Отдельный репозиторий приложения` (конкретные интеграционные и эксплуатационные действия).

Отсутствие такого раздела считается архитектурно неполной постановкой задачи.

## 6. Технологический стандарт C++

Для всех доработок C++ в этом репозитории и связанных библиотечных модулях обязательный стандарт языка: `C++20`.

Требования:

1. Новый C++ код и изменения существующего кода должны быть совместимы с `C++20`.
2. Build-конфигурация библиотек и модулей должна явно фиксировать стандарт `C++20`.
3. Task-документы с C++-изменениями должны учитывать это требование на этапе проектирования и code review.
