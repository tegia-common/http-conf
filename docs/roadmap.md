# Roadmap: архитектурные вопросы, замечания и улучшения

Дата: 2026-03-01

## 1. Текущие архитектурные вопросы

1. Должен ли `LISTENER::unload` быть доступен только системному контуру, или существует валидный внешний сценарий?

Ответ: Только системному контуру

2. Где фиксируется единый `authN/authZ gate`: централизованно перед route-dispatch или в каждой ручке?

Ответ: это нужно отдельно спроектировать. Я отдельно опишу как это сейчас реализовано

3. Какие глобальные лимиты body (`application/json`, `multipart/form-data`) считаются обязательными и где именно enforce-ятся?

Ответ: нгде и их нужно вынести в конфигурацонный файл

4. Подтверждается ли модель "новый actor на каждый запрос" как целевая по нагрузке, или нужен worker-pool подход?

Ответ: Да. Потому что актор это просто экземпляр класс. Его исполнение происходит в отдельном пуле потоков и управяется на уровне приложения

5. Должен ли `HTTP::WS` оставаться в текущем репозитории в активном состоянии, или это отложенный/вспомогательный контур?

Ответ: я не помню задумку этого актора, поэтому разумно его удалить

6. Фиксируем ли политику владения объектами (RAII-only, запрет raw owning pointers)?

Ответ: да

7. Какая утвержденная политика логирования PII/секретов в debug/error логах?

Ответ: ее нет

## 2. Текущие архитектурные замечания (audit findings)

1. В коде присутствуют публичные test-endpoints с блокирующим поведением (`sleep_for`), что создает DoS-риск.
2. `LISTENER::unload` допускает опасный паттерн управления жизненным циклом акторов по входным данным.
3. Используются `exit()` в библиотечном контуре, что недопустимо для встраиваемого модуля.
4. Парсинг request body выполняется с чтением всего payload в память, без обязательных лимитов на уровне библиотеки.
5. Аутентификация вызывается не как жесткий gateway на всех путях обработки.
6. Есть небезопасные места в парсинге cookie и работа с сырыми указателями для владения.
7. Используется `#include "*.cpp"` вместо нормальных единиц трансляции.
8. Контур `WS` выглядит частично незавершенным и требует архитектурного решения по статусу.

## 3. Предложения по улучшению архитектуры и кода

### 3.1 P0 (безопасность и эксплуатационная устойчивость)

1. Убрать/закрыть публичные `test/*` маршруты в production-профиле.
2. Ограничить `unload` ролью `SYSTEM` и ввести allowlist управляемых actor-id.
3. Удалить `exit()` из библиотечных модулей: заменить на кодовые статусы и централизованный error handling.
4. Ввести обязательные лимиты на body/header/cookie/filename и проверять их до аллокаций.

### 3.2 P1 (архитектурная консистентность)

1. Ввести единый request pipeline: `parse -> validate -> authN -> authZ -> route -> response`.
2. Зафиксировать policy ownership: `std::unique_ptr`/`std::shared_ptr` для owning-ссылок.
3. Убрать `#include "*.cpp"`, перейти на стандартную структуру `.h/.cpp`.
4. Централизовать response/header builders и общие parser utilities.

### 3.3 P2 (масштабируемость и техдолг)

1. Перейти от "read-all-in-memory" multipart к streaming-подходу.
2. Определить судьбу `HTTP::WS` (активный модуль/вывод из репозитория/рефакторинг).
3. Вынести переиспользуемые helper-компоненты в `tegia-sdk` при межрепозиторной потребности.

### 3.4 P1/P2 (I/O архитектура: единый epoll-менеджер)

1. Перейти от локальных/точечных циклов ожидания к единому `epoll`-менеджеру внешних подключений.
2. Включить в единый контур все внешние FD:
   - HTTP/FastCGI сокеты;
   - внешние TCP/Unix сокеты;
   - `pipe`/`eventfd`/служебные каналы.
3. Централизовать регистрацию FD, жизненный цикл подписок и диспетчеризацию событий.
4. Ввести единые политики:
   - backpressure;
   - таймауты;
   - лимиты по соединениям/очередям;
   - graceful shutdown.
5. Сохранить совместимость с actor-моделью через адаптер "epoll event -> actor message".

## 4. Roadmap внедрения

### Этап 1 (P0, 1-2 спринта)

1. Закрыть security-риски: test routes, unload access, `exit()`, лимиты входа.
2. Добавить базовые regression-тесты для security-critical сценариев.
3. Обновить документацию по безопасному pipeline и правилам обработки ошибок.

Критерий готовности:

1. Нет публичных debug маршрутов.
2. Нет `exit()` в библиотечном runtime-пути.
3. Все входные лимиты включены и покрыты тестами.

### Этап 2 (P1, 2-3 спринта)

1. Внедрить единый middleware-style pipeline.
2. Завершить переход на RAII для ownership-контуров.
3. Рефакторинг сборки/модулей без `#include "*.cpp"`.
4. Спроектировать и внедрить MVP единого `epoll`-менеджера для HTTP/FastCGI + служебных FD.

Критерий готовности:

1. Единая точка authN/authZ enforcement.
2. Явные границы модулей и сборки по TU.
3. Снижен объем неструктурированного техдолга.
4. Внешние I/O события обрабатываются через централизованный event-loop без дублирующих локальных wait-циклов.

### Этап 3 (P2, 3+ спринтов)

1. Streaming upload/download improvements.
2. Решение по `WS` и его финальная архитектурная роль.
3. Межрепозиторная консолидация helper-компонентов через SDK.
4. Расширение единого `epoll`-менеджера на все внешние сокеты и `pipe`-каналы.
5. Введение наблюдаемости event-loop (метрики latency, queue depth, dropped events).

Критерий готовности:

1. Улучшены показатели памяти и устойчивости под нагрузкой.
2. Устранены дубли логики между репозиториями.
3. Документация и архитектурные контракты синхронизированы.
4. Единый event-loop покрывает все внешние подключения с управляемой деградацией при пиковых нагрузках.

## 6. Что необходимо для highload-профиля

### 6.1 Архитектурные требования

1. Единый `epoll`-менеджер для всех внешних FD (`http/socket/pipe`) как основной I/O-контур.
2. Streaming-путь для больших payload (без read-all-in-memory).
3. Централизованный `authN/authZ` gateway в обязательном request pipeline.
4. Полное исключение `exit()` из библиотечного runtime-пути.
5. RAII-only ownership и отсутствие raw owning pointers.

### 6.2 Performance и capacity требования

1. Конфигурируемые лимиты:
   - body size;
   - header/cookie size;
   - max concurrent connections;
   - max in-flight requests;
   - per-route/per-tenant rate limits.
2. Backpressure policy:
   - bounded queues;
   - controlled reject (429/503) при перегрузке;
   - timeout budgets на чтение/запись/обработку.
3. Изоляция медленных контуров:
   - отдельные worker pools/queues для тяжелых маршрутов;
   - защита fast-path маршрутов от head-of-line blocking.

### 6.3 Надежность и отказоустойчивость

1. Graceful shutdown:
   - stop accepting new;
   - drain in-flight;
   - bounded shutdown timeout.
2. Fault containment:
   - ошибка одного соединения/FD не влияет на loop в целом;
   - fail-safe cleanup всех ресурсов.
3. Идемпотентные retry-сценарии на границах межсервисного взаимодействия.

### 6.4 Наблюдаемость и эксплуатация

1. Обязательные метрики:
   - p50/p95/p99 latency;
   - RPS;
   - error rate (4xx/5xx);
   - queue depth;
   - active FDs;
   - dropped/rejected requests.
2. Обязательные алерты:
   - saturation по CPU/memory/FD;
   - рост p99;
   - spike 5xx/timeout/reject.
3. Structured logging + trace correlation id через весь request lifecycle.

### 6.5 Тестирование и критерии готовности

1. Нагрузочные тесты:
   - step load;
   - spike load;
   - soak (длительный прогон).
2. Chaos/failure тесты:
   - partial dependency outage;
   - slow downstream;
   - packet loss / intermittent errors.
3. Go-live критерии:
   - стабильный p99 в целевом бюджете;
   - error-rate в допустимом пороге;
   - отсутствие утечек памяти/FD на soak тестах.
